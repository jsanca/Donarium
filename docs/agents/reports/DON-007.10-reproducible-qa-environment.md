# DON-007.10 — Reproducible QA Environment

**Status:** COMPLETE
**Owner:** Deep
**Role:** Infrastructure Engineer

## Summary

Created an isolated, disposable Docker Compose environment for QA functional
testing. The environment runs real PostgreSQL and the Donarium backend with
migrations, health checks, and no shared infrastructure with development.

## Context

Before this task, QA test cases (TC-001 and future slices) had no reproducible
way to run against a clean, isolated stack. The only PostgreSQL instance was the
development database, which accumulates test data and cannot be wiped between
QA runs.

## Environment Topology

```
donarium-qa-network (isolated)
├── donarium-postgres-qa   127.0.0.1:15432  postgres:17.4-alpine
```

## Migration Strategy

**Option A — Backend executes migrations at startup.** The server already calls
`database.RunMigrations()` in `cmd/donarium/main.go` on boot. This is the
simplest strategy and requires no additional infrastructure. The QA compose
simply waits for PostgreSQL readiness before starting the API container.

## Commands

| Command | Effect |
|---|---|
| `make qa-up` | Start QA stack (build + up) |
| `make qa-down` | Stop QA stack (preserves data) |
| `make qa-reset` | Destroy volume + recreate clean stack |
| `make qa-status` | Show service health + curl liveness/readiness |

## Safety Analysis

- **Credentials are local-only** (`donarium_qa` / `donarium_qa`), hardcoded in
  compose file. No production secrets exposed.
- **qa-reset is destructive** to QA data only. It targets
  `compose.qa.yml` explicitly — cannot accidentally destroy development volumes.
- **No port conflicts** — QA uses 15432 and 18080, distinct from defaults.
- **No external dependencies** — everything runs in Docker.

## Tradeoffs

- **Hardcoded defaults vs .env file**: Chose hardcoded defaults in
  `compose.qa.yml` so the environment works without any `.env` file. This avoids
  the risk of accidentally loading development credentials.
- **Option A (backend migrations) vs Option B (separate service)**: Chose Option A
  because the backend already runs migrations on startup. Adding a separate
  migration service would duplicate mechanism without benefit.
- **`down -v` in qa-reset vs separate volume management**: Chose `down -v` for
  simplicity. QA data is meant to be disposable.

## Open Questions and Follow-ups

- **TC-001-09 (transactional rollback)**: The QA environment is compatible but
  does not yet inject the rollback scenario. The failing executor technique from
  DON-007.8 could be adapted as a standalone test binary that the QA compose
  runs against the API.
- **Observation tools**: Could add a pgAdmin or adminer service for visual
  database inspection during QA sessions. Out of scope for this task.
- **Multi-version testing**: If Donarium needs to test against multiple
  PostgreSQL versions, the compose could be parameterized.
