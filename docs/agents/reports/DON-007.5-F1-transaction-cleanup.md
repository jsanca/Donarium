## Task 1: Simplify TransactionManager

**File:** `internal/identity/pgx/transaction.go`

**Before:**
```go
defer func() {
    if err != nil {
        _ = tx.Rollback(ctx)
    }
}()
```

**After:**
```go
defer tx.Rollback(ctx)
```

**Rationale:**
`tx.Rollback(ctx)` after a successful `tx.Commit(ctx)` is a no-op in pgx — it
returns `ErrTxClosed` which is discarded by `defer`. The unconditional `defer` is
safe because `tx` is guaranteed non-nil (we return early if `Begin` fails).

The simpler pattern has one advantage over the old code: if `fn(ctx, db)` panics,
the transaction is rolled back. The old code left the transaction open on panic
because the conditional `err != nil` check didn't fire.

Also renamed the local variable from `exec` to `db` for clarity (it's a DBExecutor,
not a raw pgx executor).

## Task 2: Review NewExecutorFromPool

**File:** `internal/identity/pgx/executor.go`

**Verdict: KEEP.** This is a necessary anti-corruption layer.

Why it exists:
1. Go does not support return-type covariance. `pgx.Pool.QueryRow()` returns
   `pgx.Row`, but `DBExecutor.QueryRow()` returns `identity.RowScanner`. Even
   though `pgx.Row` satisfies the `RowScanner` interface structurally, Go's
   interface satisfaction requires exact method signature match. So `pgx.Pool`
   cannot directly satisfy `DBExecutor`.
2. The adapter also converts `pgconn.CommandTag` to `int64` (rows affected) on
   `Exec`, keeping pgx types out of domain interfaces.
3. Both `pgxpool.Pool` and `pgx.Tx` share the same method set, so a single
   adapter (via interface parameter) covers both transactional and non-transactional
   contexts.

Alternatives considered:
- Make repos accept pgx types directly → couples domain to pgx, complicates testing
- Generate per-call-site wrappers → more code duplication
- Use Go generics → over-engineered for a single use case

Added an architectural comment explaining the rationale.
