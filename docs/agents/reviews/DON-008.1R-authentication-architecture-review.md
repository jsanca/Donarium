# DON-008.1R — Authentication Architecture Review

- **Reviewer:** Elito
- **Date:** 2026-07-21
- **Scope:** DON-008.1 — Authenticate User and Issue Session
- **Verdict:** **CHANGES REQUIRED**

## Executive Verdict

DON-008.1 has a sound initial shape: authentication is an application service,
the session issuer is an outbound port, credentials are not returned, and the
HTTP login route is small. The slice is **not ready to treat as the stable
basis for TC-002 design/execution** because production session configuration is
insecure by default, malformed Argon2id records are not safely validated, and
repository failures while loading authentication state can be suppressed or
misreported.

The custom HMAC session format is not rejected for being non-JWT. Its issuance
format is sufficiently narrow, but it is only an issuer today; no verifier
exists to enforce signature or expiry in a later protected request. The format
is therefore **ACCEPT WITH FOLLOW-UP**, not a complete session protocol.

## Architecture Assessment

The application service depends on domain ports, `PasswordHasher`,
`EmailNormalizer`, and `SessionIssuer`; it does not import Chi, HTTP cookies,
JSON, HMAC, pgx, or environment access. That direction is correct.

`LoginHandler`, however, owns a `*pgxpool.Pool` and creates a pgx-backed
`DBExecutor` before calling the service. This keeps pgx out of application code
but makes the HTTP adapter the transaction/executor composition point. It is a
coupling concern rather than evidence of domain contamination; see AAR-006.

## Session Protocol Review

**Conclusion: ACCEPT WITH FOLLOW-UP.**

The issuer emits exactly two base64url segments separated by one dot. The
payload is a fixed Go struct (`sub`, `iat`, `exp`); the signature is
HMAC-SHA-256 over the exact base64url payload bytes. The token contains only
the subject, so permissions and contexts are not frozen in the cookie.

However, `HMACSessionIssuer` only issues tokens. There is no parsing,
constant-time signature comparison, algorithm enforcement, timestamp/expiry
validation, version field, or key-rotation strategy because no verifier port or
consumer exists. A later protected-request slice must add the verifier and its
negative tests without changing the issued-token contract casually.

## Credential Security

Argon2id hashing uses explicit parameters and verification ends with
`subtle.ConstantTimeCompare`. Passwords and hashes are not returned in the
login response, and the current handler logs only the error object, not the
request payload.

The verifier nevertheless accepts an unvalidated encoded-hash structure and
silently ignores malformed parameter values. It can pass zero or attacker-sized
parameters into `argon2.IDKey`; this is unsafe for a corrupted database record
and lacks the required corrupt-hash rejection guarantee. See AAR-002.

Unknown-user authentication returns before Argon2id verification, while a wrong
password runs Argon2id. This creates an observable timing distinction in
principle. No exploitation evidence was collected, so it is recorded as an
observation rather than a required mitigation.

## Configuration Safety

`SESSION_TTL` defaults to 24h, consistent with UC-002. Invalid duration text
silently falls back to 24h; a negative duration is accepted. `SESSION_SIGNING_KEY`
has an embedded development default with no environment/profile distinction or
minimum length validation. The cookie has no `Secure`, `Max-Age`, or `Expires`
attribute and no configuration path to set `Secure=true` outside local QA.

The signing key is not logged by the reviewed code. The unsafe startup defaults
and cookie policy are nevertheless a release-blocking configuration defect.

## Persistence Review

All reviewed SQL is parameterized. `MembershipRepo.FindByUser` closes rows and
checks `rows.Err()`. The deliberate organization lookups are N+1; for the
current small context counts this is acceptable and is documented in the
implementation report.

The authentication service conflates missing entities with operational errors
in several places. `FindByEmail` and `FindByUserID` return invalid credentials
for every error; `loadPlatformGrant` returns an empty grant list for every
error; and organization lookup failures are skipped. This conflicts with
UC-002 A5 and can construct an incomplete principal from an unhealthy
persistence layer.

## HTTP Contract

Success returns `200`, JSON `principal`, and an HttpOnly, SameSite=Lax,
Path=/ cookie. `SessionToken` is excluded from JSON. Transport validation maps
to `400`; invalid credentials map to a generic `401`; unexpected service
errors map to generic `500`; and the shared runtime provides JSON `405`.

The cookie does not yet carry `Secure` or a lifetime synchronized with the
token TTL. The handler test checks only `HttpOnly`, so the complete cookie
contract is not protected by tests.

## Findings

### AAR-001 — Production can issue sessions with a known key and insecure cookie policy

- **Severity:** BLOCKER
- **Evidence:** `config.Load()` defaults `SESSION_SIGNING_KEY` to an embedded development value; `getDurationEnv` silently falls back on malformed TTL; no non-positive TTL or key-length check exists. `LoginHandler` sets no `Secure`, `MaxAge`, or `Expires`, and config has no cookie-security setting.
- **Risk:** A deployment that omits the key can mint predictable session signatures. Cookies can be sent over HTTP when an ingress or environment is misconfigured, and browser lifetime is not aligned with the token limit.
- **Recommendation:** Introduce an explicit local/QA versus deployed configuration policy. Require a non-default, sufficiently long signing key and a positive TTL outside local QA; fail startup on invalid values. Add cookie policy configuration with secure-by-default deployment behavior and set `Secure` plus `Max-Age` or `Expires` coherently with TTL.
- **Disposition:** Required before TC-002 is treated as an acceptance baseline or the slice is promoted beyond local QA.

### AAR-002 — Argon2id verification does not safely validate stored-hash parameters

- **Severity:** MAJOR
- **Evidence:** `Argon2Hasher.Verify` checks only segment count, ignores algorithm/version segments, ignores parse errors, accepts missing parameters as zero, and passes decoded parameter values directly to `argon2.IDKey`. There are no corrupt-hash tests.
- **Risk:** A corrupted or maliciously altered credential record can cause a panic, excessive resource use, or an uncontrolled failure rather than a clean credential rejection.
- **Recommendation:** Parse the exact supported Argon2id version and parameter set strictly; reject duplicate/missing/invalid values; bound memory, time, threads, salt and hash lengths before calling Argon2. Return invalid credentials for malformed records and add negative tests.
- **Disposition:** Required corrective task before TC-002 execution.

### AAR-003 — Persistence failures are confused with absence of authentication state

- **Severity:** MAJOR
- **Evidence:** `AuthenticateUserService.Execute` maps every `FindByEmail` and `FindByUserID` error to `ErrInvalidCredentials`; `loadPlatformGrant` returns `nil, nil` for every error; `loadOrganizationContexts` silently skips every organization lookup failure.
- **Risk:** Database outages and data-integrity failures can become `401` responses or successful logins with incomplete contexts, contrary to UC-002 A5's generic `500` for internal failure.
- **Recommendation:** Translate only known not-found errors into the intended generic authentication/no-context result. Propagate all operational errors to the handler's generic `500`; decide explicitly how a missing referenced organization is handled. Add tests for each repository error path.
- **Disposition:** Required before TC-002 execution.

### AAR-004 — The session format has no verification lifecycle yet

- **Severity:** MAJOR
- **Evidence:** The only session API is `SessionIssuer.Issue`; repository-wide search found no verifier, token parser, signature comparator, expiry check, or protected-request consumer.
- **Risk:** UC-002 A6 cannot be fulfilled or tested. Future code may invent incompatible token parsing or omit expiry/signature validation.
- **Recommendation:** In the next protected-request slice, define a verification port and add strict parsing, HMAC constant-time comparison, expiry/timestamp validation, and version/rotation design. Retain the current compact HMAC format unless that work uncovers a concrete incompatibility.
- **Disposition:** Follow-up required before any protected endpoint; does not request logout, refresh, or authorization expansion now.

### AAR-005 — Default organization context is nondeterministic

- **Severity:** MINOR
- **Evidence:** `MembershipRepo.FindByUser` has no `ORDER BY`; `determineDefaultContext` selects `orgCtxs[0]`. The implementation report calls this “first organization,” but persistence does not define first.
- **Risk:** A user with multiple memberships can receive a different initial experience across database plans or future migrations.
- **Recommendation:** Define and document an ordering rule (for example, creation time plus ID) in the query and test multiple memberships. Preserve the conscious organization-over-platform priority.
- **Disposition:** Required before multiple organization memberships are introduced; include in TC-002 design if the model already permits them.

### AAR-006 — HTTP handler owns pgx executor composition

- **Severity:** MINOR
- **Evidence:** `LoginHandler` depends on `*pgxpool.Pool` and calls `pgx.NewExecutorFromPool` before invoking the application service.
- **Risk:** The service remains clean, but HTTP is coupled to persistence executor creation and is the wrong long-term place for application composition/transaction policy.
- **Recommendation:** In a bounded architectural cleanup, inject an application-facing executor/provider rather than the pgx pool into the HTTP adapter.
- **Disposition:** Follow-up; not a blocker for the current correction set.

### AAR-007 — Unknown-user and wrong-password paths have a timing distinction

- **Severity:** OBSERVATION
- **Evidence:** Unknown users return before Argon2id verification; known users with a wrong password execute Argon2id.
- **Risk:** This may support account enumeration through repeated timing measurement.
- **Recommendation:** Measure before adding mitigation. If justified, perform a bounded dummy verification for unknown users.
- **Disposition:** Future security hardening; no speculative complexity required now.

### AAR-008 — UC-002 error-code wording is not represented in the HTTP envelope

- **Severity:** OBSERVATION
- **Evidence:** UC-002 names `INVALID_EMAIL` and `INVALID_CREDENTIALS`; the JSON DTO contains only textual `error`, consistent with existing setup endpoints.
- **Risk:** Client code cannot rely on stable machine-readable codes from the documented UC.
- **Recommendation:** Decide whether UC-002's “Código” is normative or illustrative; if normative, introduce a project-wide error-code contract rather than changing login alone.
- **Disposition:** Documentation/API-contract decision; not a slice-local defect.

## Required Fixes

1. Resolve AAR-001: production-safe signing-key, TTL, and cookie configuration.
2. Resolve AAR-002: strict, bounded Argon2id hash parsing and corrupt-hash tests.
3. Resolve AAR-003: preserve not-found behavior while propagating operational persistence failures as generic `500`, with tests.

## Follow-ups

- AAR-004: verification lifecycle before protected endpoints.
- AAR-005: deterministic ordering before multi-organization context is relied upon.
- AAR-006: remove pgx pool composition from the HTTP adapter in a separate cleanup.
- AAR-007: assess timing equalization only with evidence.
- AAR-008: reconcile UC error codes with the project-wide HTTP error contract.

## Positive Findings

- Application code does not import HTTP, Chi, pgx, JSON, HMAC, cookies, or environment configuration.
- HMAC-SHA-256 signing uses the exact serialized payload segment and the token excludes authorization state.
- SQL uses parameters; membership row iteration closes rows and checks `rows.Err()`.
- The response does not expose the token, password, or hash; the cookie is HttpOnly, SameSite=Lax, and Path=/.
- The user-without-context path emits no session token.

## Deferred Findings

TC-002 does not need to add logout, refresh tokens, authorization middleware,
rate limiting, account lockout, or frontend routes. Those are intentionally out
of scope for this review.

## Conclusion

The slice has an appropriate modular direction and can be corrected without
rewriting its overall design or adopting JWT. Complete AAR-001 through AAR-003
before designing TC-002 as a passing acceptance suite. Once those fixes are
reviewed, the current HMAC issuance format is suitable to carry forward with
the explicit verifier follow-up in AAR-004.
