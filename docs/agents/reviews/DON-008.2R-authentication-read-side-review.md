# DON-008.2R — Architecture Review: Authentication Read Side

- **Reviewer:** Elito
- **Date:** 2026-07-21
- **Verdict:** **CHANGES REQUIRED**
- **Closeout recommendation:** **FOLLOW-UP REQUIRED**

## Review Scope

Reviewed the authentication read side and its antecedents: DON-008.1,
DON-008.1-F1/F2/F3, DON-008.2, and DON-008.2-F1. The review covered session
cookie reading, HMAC verification, `PrincipalResolver`, middleware/context,
`GET /api/auth/me`, configuration, persistence adapters, wiring, and tests.

No production code, tests, or contracts were modified.

## Architectural Separation

The intended read-side chain is present:

```text
Session cookie → SessionVerifier → PrincipalResolver → context.Context → /api/auth/me
```

`HMACSessionHandler` owns signing/verification; `PrincipalResolverService`
owns reconstruction from domain repositories; `AuthenticationMiddleware` reads
the cookie, verifies it, resolves the principal, stores it in request context,
then calls the next handler. `MeHandler` only reads the principal and serializes
it. Login delegates principal reconstruction to the same resolver, removing the
previous duplication.

The application layer imports domain ports and no HTTP, Chi, pgx, cookie, JSON,
or environment implementation. HTTP does retain pgx-pool-to-`DBExecutor`
composition, as in the login slice; that is an adapter coupling but does not
invert application dependencies.

## Statelessness

**Confirmed.** No server-side session model, map, cache, Redis dependency, or
singleton principal state was found. Each request verifies the cookie and loads
the current User, grants, memberships, and organizations from PostgreSQL before
attaching a request-scoped principal. The token contains only `sub`, `iat`, and
`exp`; permissions are not frozen in it.

## Session Verification

The verifier has a compact and defensible HMAC protocol:

- exactly two base64url segments are required;
- signature decoding and a constant-time HMAC-SHA-256 comparison occur before
  payload decoding/trust;
- malformed base64, JSON, empty subject, non-UUID subject, empty timestamps,
  expired timestamps, reversed timestamps, and future `iat` beyond one minute
  are rejected;
- a `Clock` port supports deterministic time tests;
- malformed-input tests exercise no-panic behavior.

The verifier returns the same public `401` contract through middleware for
missing, invalid, expired, and deleted-user authentication states. The exact
expiration boundary (`now == exp`) is not tested and is a minor follow-up.
Versioning and key rotation are not in the issued format yet; this is an
explicit future protocol concern, not a reason to replace the implementation
with JWT.

## Principal Resolution

`PrincipalResolverService` loads the User, platform grant, memberships, and
each referenced Organization on each request. Operational repository failures
are wrapped and reach middleware as `500`; known User absence and no usable
context become the generic `401` outcome. Login delegates to the same resolver,
so current contexts are reconstructed through one component.

The remaining defect is deterministic default selection: the membership query
has no `ORDER BY`, while `determineDefaultContext` selects index zero. This is
not a safe definition of a default context for a multi-membership user.

## Middleware and Context

`AuthenticationMiddleware` performs the expected narrow sequence: read cookie,
verify token, parse subject, resolve principal, place it in context, invoke next
once. It contains no role decision or business authorization. `contextKey` is a
private typed struct, and `PrincipalFromContext`/`WithPrincipal` use
request-scoped `context.WithValue` safely.

There is, however, a separate `authz_middleware.go` containing implemented and
tested platform/organization role guards. It is not mounted in the reviewed
runtime, but its presence is authorization implementation outside the agreed
slice and directly violates the read-side scope.

## HTTP Contract and Error Propagation

For `/api/auth/me`, the handler returns principal JSON only; `SessionToken` is
excluded from serialization. The cookie, signing key, password, and credential
hash are not present in the response. The middleware maps cookie/token/deleted
user failures to `401 {"error":"authentication required"}` and resolver
operational errors to `500 {"error":"internal server error"}`.

`MeHandler` checks `GET` and returns JSON `405`; the shared runtime provides
the standard JSON method-not-allowed response. Current tests exercise the
handler directly, not the complete Chi route tree for the exact external path
`/api/auth/me`; this leaves an integration coverage gap.

## Test Coverage

Reviewed test source confirms coverage for verifier structure/signature/base64/
JSON/UUID/expiration/future clock/no panic, middleware short-circuiting and
next-once behavior, context propagation, `401`/`500`, and me-handler JSON/no
token/`405`/content type.

Executed without database mutation:

```text
go test ./internal/identity/application/authentication ./internal/identity/http ./internal/platform/config
PASS
```

`server/internal/identity/pgx` tests were inspected but not run because their
package-level test setup may initialize and drop tables in a database. This
review did not need to mutate a test database.

Meaningful remaining coverage gaps:

- complete Chi routing of exact `/api/auth/me` with middleware;
- deterministic multi-membership default context;
- expiration equality boundary;
- integration evidence that role middleware is absent from runtime routes.

## Findings

### AAR-001 — Authorization middleware is implemented inside the authentication read-side slice

- **Severity:** MAJOR
- **Description:** `server/internal/identity/http/authz_middleware.go` implements `HasPlatformRole`, `HasOrganizationRole`, `RequirePlatformRole`, and `RequireOrganizationRole`; `authz_middleware_test.go` tests role-based `403` behavior.
- **Architectural impact:** These are authorization decisions, explicitly out of scope. They conflate the authentication foundation with policy enforcement and create an unreviewed API surface before a protected business endpoint exists.
- **Evidence:** The role guards are not mounted by `IdentityRuntime`, so no runtime authorization leakage was found; their implementation and tests nevertheless exist in the slice.
- **Recommendation:** Remove or move this unmounted authorization implementation to a separately planned authorization slice. Keep only `AuthenticationMiddleware` and, if needed, the principal-presence check justified by the authentication route.
- **Disposition:** Required before DON-008.2 closeout.

### AAR-002 — Default organization context remains nondeterministic

- **Severity:** MAJOR
- **Description:** `MembershipRepo.FindByUser` queries memberships without `ORDER BY`; `determineDefaultContext` chooses the first returned organization context.
- **Architectural impact:** Stateless reconstruction can yield different default experiences for the same persisted user. The issue affects both login and `/api/auth/me` because they correctly reuse the same resolver.
- **Recommendation:** Define the product ordering rule and enforce it in persistence (for example explicit primary/default flag, or stable creation-time and ID ordering), then add a multi-membership test through `PrincipalResolver`.
- **Disposition:** Required before DON-008.2 closeout.

### AAR-003 — Exact externally documented route is not integration-tested

- **Severity:** MINOR
- **Description:** Middleware and `MeHandler` are tested directly, but no test constructs the Identity runtime/Chi route tree and calls the exact public path `GET /api/auth/me`.
- **Architectural impact:** Route composition, path normalization, middleware ordering, and final `405` behavior are inferred rather than protected by a regression test.
- **Recommendation:** Add one focused router-level test in a follow-up, using fakes for verifier/resolver and asserting the public path, `401`, `200`, JSON content type, and token absence.
- **Disposition:** Follow-up; not a reason to add authorization.

### AAR-004 — Session protocol lacks explicit version/rotation and expiry-boundary policy

- **Severity:** OBSERVATION
- **Description:** The format is securely verified today but has no version/key identifier; expiration uses `now.After(exp)`, and the `now == exp` boundary is not specified or tested.
- **Architectural impact:** Future key rotation or protocol evolution will need a coordinated migration. The ambiguity is not an active signature-validation failure.
- **Recommendation:** Before token rotation or multi-key support, introduce an explicit version/key-selection policy and document the expiry boundary. Add a boundary test when the policy is chosen.
- **Disposition:** Future session-protocol slice.

## Positive Findings

- Stateless request-by-request reconstruction is correctly implemented; no hidden session storage was found.
- The HMAC verifier validates the signature before decoding or trusting payload content and uses constant-time comparison.
- Session claims contain only a UUID subject and timestamps; authorization state is resolved from persistence.
- `PrincipalResolver` is reused by login and read side, eliminating duplicated principal assembly.
- Middleware has a cohesive happy-path and short-circuits failures without calling the next handler.
- Typed context keys and helper APIs are request-scoped and safe.
- Operational resolver failures are distinct from authentication failures at the HTTP boundary (`500` vs shared `401`).
- Config, HTTP, and application tests executed for this review pass.

## Risk Assessment

| Dimension | Assessment |
| --- | --- |
| Maintainability | Good component separation; authorization code in this slice adds avoidable confusion. |
| Extensibility | Resolver and verifier ports are reusable; version/rotation needs explicit future design. |
| Security | HMAC verification and stateless resolution are sound; no permissions in tokens. No authorization route is currently mounted. |
| Testability | Clock/verifier/resolver/context seams are strong; public router composition and multi-membership order need coverage. |

## Deferred Findings

This review does not request logout, refresh, caching, Redis, authorization
policy, protected business endpoints, or a JWT migration. No authorization
logic was found mounted in runtime routes.

## Recommendation

**DON-008.2: FOLLOW-UP REQUIRED.** Resolve AAR-001 and AAR-002, then add the
focused route-composition test from AAR-003. After that, DON-008.2 is ready for
closeout without broadening the feature set.
