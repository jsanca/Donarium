# EP-001.01R — Post-login Shell Engineering Review

- **Reviewer:** `engineering-reviewer` (OSK role v0.1.0)
- **Date:** 2026-09-02
- **Verdict:** **CHANGES REQUIRED**
- **Closeout recommendation:** **FOLLOW-UP REQUIRED**

## Review Scope

Independently reviewed the EP-001.01 implementation (post-login shell, router,
and empty-state routing decision) and its durable evidence. The review examined
the implementation source in `client/src/` against the materialized task
`EP-001.01-post-login-shell-and-router.md`, the approved plan EP-001 (r3),
ADR-003, and the completion report.

Implementation files inspected directly: `App.tsx`, `router.tsx`,
`lib/api.ts`, `lib/returnUrl.ts`, `auth/AuthContext.tsx`, `auth/RequireAuth.tsx`,
`shell/AuthenticatedShell.tsx`, `routes/RootRedirect.tsx`, `routes/ZeroProperties.tsx`,
`routes/PortfolioPlaceholder.tsx`, `routes/PropertyHomePlaceholder.tsx`,
`routes/InvitationAcceptPlaceholder.tsx`, `routes/NotFound.tsx`,
`shared/ui/ErrorBoundary.tsx`, `shared/ui/RouteError.tsx`,
`shared/i18n/{index,en,es}.ts`, `features/authentication/components/LoginForm.tsx`,
`features/authentication/pages/LoginExperience.tsx`, `vite.config.ts`,
`main.tsx`. Backend session semantics were confirmed against
`server/internal/identity/http/auth_middleware.go` and `me_handler.go`.

No production code, tests, or configuration were modified.

## Executive Summary

The routing shell is architecturally sound: the `AuthProvider` → `RequireAuth`/
`PublicOnly` → `RootRedirect` → `AuthenticatedShell` composition is coherent,
return-URL sanitization on the login path correctly prevents open redirects,
ADR-003 is properly authored, and the lazy-loaded placeholders respect the
property/invitation/payment boundaries owned by EP-001.02/.03/.12/.13/.14.
Three material concerns require resolution before EP-001.01 can be safely
considered `DONE`: (1) the "Sign out" control is a misleading no-op that leaves
the authenticated session valid and immediately bounces the user back into the
shell; (2) `RootRedirect` conflates HTTP 401 (unauthenticated) with "zero
properties", presenting an authentication failure as a legitimate empty
portfolio; and (3) EP-001.01 realized EP-001.06's owned i18n scope while still
declaring EP-001.06 as a dependency, leaving the plan graph inconsistent.

## Review focus assessment

### 1. Dependency and ownership integrity

EP-001.01 declares EP-001.06 as a dependency ("Bilingual copy must consume the
i18n keys emitted by EP-001.06"). The implementation, however, performed
EP-001.06's stated outcome directly: it created `en.ts`, expanded `es.ts` with
the full EP-001 key set, and implemented A-9 language detection in
`shared/i18n/index.ts` (`detectLanguage()` — `localStorage` → `navigator.language`
→ ES fallback). This is precisely the scope EP-001.06 owns. The dependency edge
`N06 → N01` is therefore inverted in practice: the consumer produced what the
producer was to produce. This is a graph/boundary inconsistency (see AAR-003),
not a runtime defect — the i18n work itself is complete and consistent.

### 2. Authentication semantics for `GET /api/properties`

`RootRedirect` maps both 401 and 404 to `{ status: 'zero' }` → `/welcome`.
The 404 case is an acceptable, clearly-scoped temporary seam for "endpoint not
yet implemented" (EP-001.02 not landed). The 401 case is not: a 401 means the
session is missing, expired, or invalid (confirmed in `auth_middleware.go`,
which returns 401 for missing/expired/invalid sessions), which is semantically
different from "the user has zero properties". Treating them as equivalent
presents an expired/invalidated session as a legitimate empty portfolio (see
AAR-002). This is a real defect that will activate as soon as EP-001.02 lands
and `GET /api/properties` returns a genuine 401 under `RequireAuthentication`.

### 3. Sign-out behavior

`AuthenticatedShell.handleSignOut` performs `navigate('/login', { replace: true })`
and nothing else. `AuthProvider` exposes no `logout`; the principal is not
cleared and the httpOnly session cookie is not (and cannot be, client-side)
invalidated. Because `PublicOnly` redirects authenticated users away from
`/login` back to `/`, clicking "Sign out" navigates to `/login` and is
immediately bounced back into the authenticated shell. The UI therefore
presents a working-looking "Sign out" control (with `LogOut` icon and
`shell.signOut` label) that does not sign the user out (see AAR-001). This is a
security-relevant correctness defect on shared devices, not a neutral
placeholder.

### 4. Scope and downstream boundary preservation

No property, invitation, or payment *behavior* was implemented — the
placeholders (`ZeroProperties`, `PortfolioPlaceholder`,
`PropertyHomePlaceholder`, `InvitationAcceptPlaceholder`) are scaffolding that
EP-001.02/.03/.04/.12/.13/.14 will replace. The only boundary entered by
EP-001.01 is the i18n scope owned by EP-001.06 (see AAR-003).

### 5. Contract and evidence quality

- Routing behavior: verified by reading `router.tsx` and `RootRedirect.tsx`; coherent.
- Return-URL preservation and open-redirect protection: the login path uses
  `sanitizeReturnUrl` (rejects scheme, `//`, and CRLF). `LoginForm` and
  `RequireAuth` both rely on it. A weaker, divergent inline sanitizer exists in
  `PublicOnly` (see AAR-006).
- ADR-003: authored, bilingual, considers three alternatives, records authority.
- Error handling: H-4 envelope parsing (`parseApiError` reads JSON `{ error }`
  and the `Allow` header) is well implemented; per-route and global boundaries
  exist. Several error/loading states bypass i18n with hardcoded English (see
  AAR-005).
- Build evidence: independently reproduced — `cd client && npm run build`
  passes (`tsc -b && vite build`, 2118 modules, lazy chunks split as reported).
- Automated verification: none beyond the build; no client test runner is
  provisioned. This is a recorded limitation, not hidden.
- Limitations: the report accurately records the missing logout endpoint, the
  unimplemented `GET /api/properties`, and the absence of an e2e harness, but it
  characterizes the sign-out redirect as "acceptable placeholder behavior"
  without acknowledging that `PublicOnly` immediately undoes it (AAR-001), and
  it claims "i18n parity" while several error/loading states are hardcoded
  English (AAR-005).

## Findings

### AAR-001 — Sign-out is a misleading no-op that leaves the session valid

- **Severity:** MAJOR
- **Category:** security / implementation
- **Description:** `AuthenticatedShell.handleSignOut` (`shell/AuthenticatedShell.tsx:13-17`)
  only calls `navigate('/login', { replace: true })`. `AuthContext` exposes no
  `logout` and the principal is never cleared. The session cookie is httpOnly
  and cannot be cleared client-side. `PublicOnly` (`auth/RequireAuth.tsx:59-61`)
  redirects any `authenticated` user away from `/login` back to `/` (or the
  sanitized `returnUrl`).
- **Evidence:** `AuthenticatedShell.tsx:13-17`; `AuthContext.tsx:46-58` (no
  `logout`, only `setPrincipal`); `RequireAuth.tsx:49-74` (`status ===
  'authenticated'` → `Navigate`).
- **Impact:** Clicking "Sign out" navigates to `/login` and is immediately
  bounced back into the authenticated shell; the user believes they have signed
  out but the session remains valid. On a shared device this is a
  security-relevant correctness defect. It also contradicts ADR-003, which
  specifies an `AuthProvider` exposing `logout` (see AAR-004).
- **Recommendation:** Until a real `POST /api/auth/logout` endpoint exists (a
  backend change outside EP-001.01's "no backend changes" constraint), disable
  or remove the sign-out control rather than presenting a non-functional one.
  If Product Authority wants sign-out in this slice, it must be planned as a
  backend-capable node.
- **Disposition:** Required before EP-001.01 closeout. Responsible node:
  `software-engineer` (EP-001.01); if a logout endpoint is desired, this needs a
  plan decision (`product-architect`).

### AAR-002 — `RootRedirect` conflates HTTP 401 with "zero properties"

- **Severity:** MAJOR
- **Category:** implementation (semantic/operational correctness)
- **Description:** `RootRedirect` catches a 401 from `GET /api/properties` and
  sets `{ status: 'zero' }`, routing the user to `/welcome` ("Register a
  property"). The code comment claims it should "let parent redirect", but it
  does not — it maps to zero.
- **Evidence:** `routes/RootRedirect.tsx:31-34` (401 → `'zero'`) and `:61`
  (`'zero'` → `Navigate /welcome`); `server/internal/identity/http/auth_middleware.go:56-63`
  (401 for missing/expired/invalid session).
- **Impact:** An expired or invalidated session (e.g., deleted user, TTL expiry
  between `/api/auth/me` succeeding and `/api/properties` being called) is
  presented as a legitimate empty portfolio instead of re-authentication. This
  becomes a live defect once EP-001.02 implements `GET /api/properties` under
  `RequireAuthentication`.
- **Recommendation:** On 401, propagate the unauthenticated state to `AuthProvider`
  (e.g., call `refresh()` or set principal to null) so `RequireAuth` redirects to
  `/login`, rather than mapping to zero. Keep the 404 → zero seam as a
  time-boxed, explicitly-removed-when-EP-001.02-lands behavior (see AAR-007).
- **Disposition:** Required before EP-001.01 closeout. Responsible node:
  `software-engineer` (EP-001.01).

### AAR-003 — EP-001.01 realized EP-001.06's owned i18n scope

- **Severity:** MAJOR
- **Category:** task/graph (boundary)
- **Description:** EP-001.01 declares EP-001.06 as a dependency, yet created
  `en.ts`, expanded `es.ts` with the full EP-001 key set, and implemented A-9
  language detection — the intent/outcome assigned to EP-001.06 ("gains an EN
  bundle… New keys for the entire EP-001 experience… Language defaults per
  A-9"). The dependency edge `N06 → N01` is inverted in practice.
- **Evidence:** `client/src/shared/i18n/en.ts` (new), `es.ts` (expanded),
  `index.ts:8-22` (`detectLanguage`); task EP-001.01 "Depends on: EP-001.06";
  plan EP-001 §Work nodes, EP-001.06 intent.
- **Impact:** The plan graph no longer matches reality. EP-001.06's remaining
  value is unclear; downstream consumers EP-001.04/.05/.14 still list EP-001.06
  as a dependency and may redundantly redo or conflict with work already
  completed here.
- **Recommendation:** Reconcile the graph. Minimal outcome: mark EP-001.06 as
  absorbed/superseded for its bundle-creation and A-9 scope, narrow its
  remaining scope to parity verification across the full EP-001 experience and
  A-9 default demonstration in `{ES, EN, other}` browsers (or fold that into
  EP-001.09/EP-001.11), and update the dependency edges for .04/.05/.14. This
  is a plan-owner decision, not an executor defect — the i18n code is complete.
- **Disposition:** Resolve before EP-001.01 closeout via graph reconciliation.
  Responsible node: `product-architect` (plan) / `knowledge-curator` (graph
  materialization).

### AAR-004 — ADR-003 `AuthProvider` contract drift (missing `logout`)

- **Severity:** MINOR
- **Category:** documentation/contract
- **Description:** ADR-003 §Decisión specifies `AuthProvider` exposing
  `{ principal, loading, error, refresh, logout }`. The implementation exposes
  `{ status, principal, error, refresh, setPrincipal }` — no `logout`, and a
  `status` enum instead of a `loading` boolean.
- **Evidence:** `docs/adr/ADR-003-client-routing.md:31`;
  `auth/AuthContext.tsx:7-13,46-58`.
- **Impact:** The recorded decision no longer matches the code; the missing
  `logout` is the concrete manifestation behind AAR-001.
- **Recommendation:** Amend ADR-003 to match the implemented surface (or add
  `logout` when AAR-001 is resolved), so the decision remains authoritative.
- **Disposition:** Follow-up with AAR-001.

### AAR-005 — Error and loading states bypass i18n (hardcoded English)

- **Severity:** MINOR
- **Category:** verification / i18n
- **Description:** The global error boundary, `RequireAuth` error/loading
  states, `RootRedirect` error/loading, and the lazy-route `Suspense` fallback
  use hardcoded English. The `errorBoundary.*` and `common.*` keys defined in
  both bundles are never consumed.
- **Evidence:** `shared/ui/ErrorBoundary.tsx:47-64`; `auth/RequireAuth.tsx:11-15,31-39`;
  `routes/RootRedirect.tsx:53-55,67-74`; `router.tsx:26-28`; unused keys in
  `shared/i18n/en.ts` (`errorBoundary`, `common`) and `es.ts`.
- **Impact:** The "bilingual" claim is overstated for edge/error states,
  weakening the WCAG AA / bilingual baseline for exactly the moments a user
  most needs clear localized messaging.
- **Recommendation:** Route these states through `t()` (a functional wrapper or
  `useTranslation` where hooks are available) and consume the existing keys.
- **Disposition:** Follow-up; not a hard blocker but should be recorded.

### AAR-006 — Divergent return-URL sanitization in `PublicOnly`

- **Severity:** MINOR
- **Category:** implementation (consistency)
- **Description:** `PublicOnly` re-implements return-URL sanitization inline
  and omits the CRLF check, diverging from the shared `sanitizeReturnUrl`.
- **Evidence:** `auth/RequireAuth.tsx:56-57` vs `lib/returnUrl.ts:5-14`
  (includes CRLF rejection).
- **Impact:** Two security-relevant parsers that can drift. Client-side
  `Navigate` is not an HTTP header-injection vector, so impact is low today, but
  the duplication invites future divergence on a function whose whole purpose is
  to prevent open redirects.
- **Recommendation:** Replace the inline check in `PublicOnly` with the shared
  `sanitizeReturnUrl` helper.
- **Disposition:** Follow-up.

### AAR-007 — 404 → zero seam and a misleading `fetchProperties` comment

- **Severity:** OBSERVATION
- **Category:** documentation / boundary
- **Description:** `fetchProperties` throws on `!res.ok`, yet its trailing
  comment claims "if the endpoint 404s/empty, treat as zero properties"; the
  404 → zero mapping actually lives in `RootRedirect`'s catch. The 404 seam is
  a deliberate, acceptable bridge until EP-001.02 lands.
- **Evidence:** `lib/api.ts:96,107-108`; `routes/RootRedirect.tsx:35-39`.
- **Impact:** Misleading in-code documentation; the seam must not survive
  EP-001.02 (a real 404 from an implemented endpoint should surface an error,
  not "zero properties").
- **Recommendation:** Correct the comment; ensure EP-001.02 removes the 404 →
  zero branch and adds coverage for the unimplemented-seam removal.
- **Disposition:** No action now; must be revisited at EP-001.02.

## Positive Findings

- The `AuthProvider → RequireAuth/PublicOnly → RootRedirect → AuthenticatedShell`
  composition is coherent and correctly isolates the auth gate from routing.
- `AuthProvider` correctly treats a 401 from `/api/auth/me` as unauthenticated
  and clears the principal; the login path reuses the same principal shape.
- Return-URL sanitization on the login path (`sanitizeReturnUrl`) rejects
  scheme, `//`, and CRLF — open redirect is not possible via `LoginForm`/
  `RequireAuth`.
- ADR-003 is well-formed: bilingual, three alternatives considered, authority
  and evolution recorded.
- H-4 error-envelope handling (`parseApiError` reading JSON `{ error }` and the
  `Allow` header) is correctly implemented and reused by login and routing.
- No property, invitation, or payment behavior was absorbed; placeholders are
  explicit scaffolding that downstream nodes own.
- WCAG AA practices are consistently applied (visible focus ring, skip link,
  `aria-live`/`role`, `prefers-reduced-motion`, ≥44px touch targets).
- Code-splitting is real and independently verified by build output (2118
  modules, per-route lazy chunks).
- Vite `/api` proxy is correctly configured so `npm run dev` works against the
  local server.

## Deferred Findings

- No request for a logout endpoint, refresh tokens, session caching, or backend
  changes is made here; those are out of EP-001.01 scope.
- Invitation acceptance authorization (401/404/410/403/201) and property
  authorization semantics are owned by EP-001.13 / EP-001.07 and are not
  evaluated in this review.
- Automated e2e/unit client verification is absent by plan (no runner
  provisioned); QA verification is delegated to EP-001.09.

## Risk Assessment

| Dimension | Assessment |
| --- | --- |
| Maintainability | Strong component separation and lazy seams; divergent return-URL sanitizers and unused i18n keys add minor drift. |
| Extensibility | Lazy-loaded placeholders and a tolerant properties adapter are well-suited to downstream plug-in. |
| Security | Return-URL protection on the login path is sound; the misleading sign-out (AAR-001) and the 401→zero conflation (AAR-002) are the material security/correctness risks. |
| Testability | No client test runner; build-only verification. Routing/auth logic is unit-testable by design but currently untested. |

## Recommendation

**Verdict: CHANGES REQUIRED. Closeout: FOLLOW-UP REQUIRED.**

EP-001.01 may **not** remain `DONE` as-is. Before closeout:

1. Resolve **AAR-001** — disable/remove the non-functional sign-out control (or
   obtain a plan decision for a logout endpoint). Responsible: `software-engineer`
   (with `product-architect` if a logout endpoint is desired).
2. Resolve **AAR-002** — propagate 401 to the auth layer instead of mapping to
   zero properties. Responsible: `software-engineer`.
3. Resolve **AAR-003** — reconcile the plan graph for EP-001.06. Responsible:
   `product-architect` / `knowledge-curator`.
4. Record follow-ups for **AAR-004**, **AAR-005**, **AAR-006**; revisit
   **AAR-007** at EP-001.02.

**Downstream handoff:** EP-001.04 and EP-001.14 may proceed against the current
shell — the routing shell, auth gate, return-URL preservation, and lazy seams
are sound and safe to build on. They should be aware that (a) sign-out is
non-functional until AAR-001 is resolved, and (b) the i18n bundles they were
told to consume from EP-001.06 already exist from EP-001.01, so they need not
wait for EP-001.06's original deliverable.

**EP-001.06 disposition:** Its bundle-creation and A-9 detection scope has been
realized by EP-001.01. Recommend narrowing EP-001.06 to parity/behavior
verification for the full EP-001 experience (or folding that into EP-001.09 /
EP-001.11) and updating the dependency edges of EP-001.04/.05/.14 accordingly.
