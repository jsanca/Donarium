## Findings

### 03R-001 — External-email validation differs between domain and DB constraint

- **Severity:** MINOR
- **Type:** implementation defect (validation-boundary inconsistency)
- **Affected:** `properties/party.go:63-72`; `007_property_stakeholders.up.sql:15-17`;
  `properties/pgx/stakeholder_repository.go:46-57`; `properties/http/handler.go:184`.
- **Evidence:** `Party.Validate()` accepts an external email when
  `mail.ParseAddress` succeeds and it contains `@` (e.g. `foo@bar`, no dot in the
  domain). The migration's `chk_external_email` regex
  `'^[^@]+@[^@]+\.[^@]+$'` requires a dot. A `foo@bar`-style address passes
  domain validation, then fails the DB CHECK at insert; `StakeholderRepository.Create`
  returns the raw CHECK error (not `ErrInvalidParty`), and `mapDomainError`
  defaults to 500.
- **Impact:** A client validation error (address rejected by the DB's stricter
  rule) surfaces as a 500 "internal server error" instead of a 400.
- **Recommendation:** Align the two — either enforce the same shape in
  `Party.Validate()` (e.g. require a dot in the domain) or relax the CHECK to
  match `mail.ParseAddress`, and map CHECK violations to `ErrInvalidParty` (400).
- **Disposition:** Follow-up; owner `software-engineer`.

### 03R-002 — Infrastructure errors misclassified as domain validation (400)

- **Severity:** MINOR
- **Type:** error-propagation concern
- **Affected:** `properties/application/service.go:339-361` (`stakeholdersTieActor`),
  `:363-379` (`checkUserExists`/`checkOrganizationExists`).
- **Evidence:** `stakeholdersTieActor` runs
  `db.QueryRow(...).Scan(&exists)` and only acts on `err == nil`, so any real DB
  error (including connection failure) is silently treated as "no membership" and
  ultimately becomes `ErrNoStakeholder` (400). `checkUserExists`/
  `checkOrganizationExists` wrap **any** error as "user not found" /
  "organization not found", which is string-matched and mapped to
  `ErrInvalidParty` (400).
- **Impact:** Transient infrastructure failures during stakeholder validation are
  reported as client (400) errors rather than 500, and the membership-check path
  drops the underlying error entirely.
- **Recommendation:** Distinguish `pgx.ErrNoRows` from other errors; return
  infrastructure errors unwrapped so they surface as 500.
- **Disposition:** Follow-up; owner `software-engineer`.

### 03R-003 — Legacy `NewService` path diverges from production access enforcement

- **Severity:** MINOR
- **Type:** architectural concern (divergent code path)
- **Affected:** `properties/application/service.go:52-58, 154-159, 182, 203-208,
  253-258, 381-403`.
- **Evidence:** Production wiring uses `NewServiceWithStakeholders`
  (`main.go:97`). The legacy `NewService` (nil `stakeholderRepo`) skips the
  organization-membership tying check (only `tiesActorDirectly`), falls back to
  `CreatedBy` in `GetByID`, and inserts via a duplicated `insertStakeholderDirect`
  that (unlike `StakeholderRepository.Create`) does not lowercase the external
  email. It is exercised only by tests (`service_test.go:70` `newService`).
- **Impact:** Tests built on `newService` validate different behavior than
  production (the finalized access rule is not enforced there), and a second
  insert/validation path invites drift. No production defect, since the legacy
  constructor is not wired in `main.go`.
- **Recommendation:** Remove `NewService` and `insertStakeholderDirect`; migrate
  the legacy tests to `NewServiceWithStakeholders` so tests and production share
  a single path.
- **Disposition:** Follow-up; owner `software-engineer`.

### 03R-004 — Unused/speculative code

- **Severity:** OBSERVATION
- **Affected:** `properties/repository.go:14`; `properties/pgx/stakeholder_repository.go:150-210`.
- **Evidence:** `FindAccessiblePropertyIDs` is declared and implemented but never
  called by any consumer. `timeScan` (with its `Scan` method) and
  `var _ = pgx.ErrNoRows` are dead scaffolding.
- **Impact:** None functional; adds surface area to maintain.
- **Recommendation:** Remove `FindAccessiblePropertyIDs` (re-add when a consumer
  exists) and the dead `timeScan`/`var _` lines.
- **Disposition:** No action required now.

### 03R-005 — Stakeholder attribution not exposed over HTTP

- **Severity:** OBSERVATION
- **Type:** downstream dependency
- **Affected:** `properties/http/handler.go` (no stakeholder read endpoint).
- **Evidence:** `RegisterProperty` returns 201 with only `PropertyResponse`
  (`handler.go:92-94`); stakeholders are persisted and queryable via
  `StakeholderRepository.FindByProperty`, but no HTTP path reads them. The plan's
  Appendix B defines no stakeholder endpoint.
- **Impact:** EP-001.03 "supplies attribution to EP-001.04" only at the
  persistence/repository layer; EP-001.04 must add the read path (extend
  `GET /api/properties/{id}` or add a stakeholders endpoint) to render the
  Property Home header.
- **Recommendation:** Record as an EP-001.04 input; no change in this node.
- **Disposition:** Owner `software-engineer` (EP-001.04).

## Review-question assessment

- **Party model / discriminated persistence** — PASS. Three variants with
  column-coherence `CHECK`s (`chk_party_user/org/external`) match ADR-005.
- **Access rule finalization** — PASS. `FindAccessibleByUser` and `HasAccess`
  correctly resolve `UserRef` direct OR `OrganizationRef` via `memberships`;
  `ExternalParty` never confers access. `DISTINCT` handles dual-direct+org access.
- **A-12 uniqueness** — PASS. Enforced at the DB (`uq_property_stakeholder`) and
  in-service dedup; same Party may hold both OWNER and MANAGER.
- **Atomicity** — PASS. Property + stakeholders persist in one transaction and
  roll back on any failure.
- **Non-disclosure** — PASS. `GetByID` returns `ErrPropertyNotFound` for both
  not-found and unauthorized.
- **`Membership`/`OrganizationRole` untouched** — PASS (H-2). No identity schema
  change; ADRs reference current `Membership`/`PlatformGrant` semantics.
- **ADR-004/005** — PASS. Correct rationale (per-property relation vs extending
  `OrganizationRole`; discriminated Party), linked, placed under
  `docs/adr/`.
- **Migration** — PASS. Additive, reversible, CHECK/unique/index appropriate;
  ready for EP-001.10.
- **H-2/H-3/H-4** — PASS. No contradicted citations; DB tests fail explicitly
  (verified); JSON + `Allow` preserved across 400/401/404/405/409.

## Positive Findings

- The Party/PropertyStakeholder design faithfully realizes all four Stitch
  options without ad-hoc columns.
- Access-rule SQL is correct and consistent across `FindAccessibleByUser`,
  `HasAccess`, and `FindAccessiblePropertyIDs`.
- In-service dedup key (`partyType|reference|role`) matches the DB unique index
  composition, so both layers agree on A-12.
- Transaction boundary is correct: stakeholder failure rolls back the property.
- Domain keeps its anti-corruption `DBExecutor` (no `identity` import) even though
  the schema references `users`/`organizations` — a clean Go-layer boundary.
- Error mapping is centralized and complete (`mapDomainError` covers all new
  domain errors, including 409 for duplicates).

## Verdict

**PASS WITH FINDINGS.** No BLOCKER or MAJOR findings. The implementation
correctly realizes EP-001.03, finalizes the access rule, and respects identity
boundaries. EP-001.03 may be accepted from the engineering-review perspective.
