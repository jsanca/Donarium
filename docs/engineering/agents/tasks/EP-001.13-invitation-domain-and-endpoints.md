## Intent and outcome

Introduce the `Invitation` entity — `(InvitationID, PropertyID, IntendedRecipientEmail, OfferedRole, IssuedBy, IssuedAt, ExpiresAt?, AcceptedAt?, AcceptedBy?, RevokedAt?, Token)` — migration `009_invitations`, opaque token generation, and endpoints:

- `POST /api/properties/{id}/invitations` — issue. Authorization per plan A-13 (OWNER or MANAGER stakeholder of the target Property). **Response includes the shareable acceptance URL.**
- `GET /api/properties/{id}/invitations` — list invitations for a given Property (issuer-side view).
- `GET /api/invitations/{token}` — return invitation display details for the intended recipient; four-outcome authorization per the plan's Invitation authorization rule.
- `POST /api/invitations/{token}/accept` — accept; on success, create `PropertyStakeholder(UserRef(u.ID), OfferedRole)` in the same transaction and record `AcceptedAt`/`AcceptedBy`.
- `DELETE /api/invitations/{token}` — revoke; permitted for the issuer or for any OWNER stakeholder of the Property.

## Relevant context and requirements

- **No in-app pending-invitations panel. No email delivery. Delivery is entirely external.** Invitation creation and delivery are separate concerns (plan OP-9).
- **Acceptance never creates accounts.** If no account exists for `IntendedRecipientEmail`, the invitation remains dormant until an account is created via another flow (plan OP-10).
- Identity match uses plan A-14: authenticated User's normalized email equals normalized `IntendedRecipientEmail`.
- Authorization outcomes on `/api/invitations/{token}` and `/api/invitations/{token}/accept`:
  - unauthenticated → **401 Unauthorized** (client redirects to login, preserves return URL);
  - token not found or revoked → **404 Not Found**;
  - token expired → **410 Gone** (plan A-11) with a machine-readable outcome envelope distinct from 401/403/404;
  - authenticated but identity does not match → **403 Forbidden**;
  - valid + intended → **200 OK** (GET) or **201 Created** (accept) with the new stakeholder record.
- Complies with plan hygiene **H-2**, **H-3**, **H-4**.

## Constraints / established direction

- Token is opaque. **Do not** adopt the 16-character format from Stitch as a requirement.
- Expiration returns HTTP 410 Gone.
- **ADR-006** authored: Invitation semantics — recipient identification, opaque token, expiration representation (A-11), four-outcome authorization, decoupling from delivery.
- Do not introduce any delivery mechanism (email, SMS, in-app notification, in-app pending list) in this node or its report.

## Expected evidence

- Integration tests exercising each authorization outcome (401 / 404 / 410 / 403 / 200 / 201) and the revoke path.
- Test evidence that a dormant invitation (no matching account) returns the correct outcome and does not create an account.
- ADR-006 authored and linked.
- Draft SQL for `009_invitations` available for EP-001.10.
- Explicit assertion in the report that no delivery mechanism is introduced.
- Report at `docs/engineering/agents/reports/EP-001.13-invitation-domain-and-endpoints.md`.

## Handoff / stop condition

Invitation capability exposes the URL and validates acceptance. **Delivery is outside this node forever.** The `POST /api/properties/{id}/invitations` response returns the shareable URL for external distribution by the inviter.
