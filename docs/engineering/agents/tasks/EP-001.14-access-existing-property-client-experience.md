## Intent and outcome

Zero Properties page includes an "Access an Existing Property" informational area explaining that access happens by opening the invitation URL shared by the inviter (not by browsing an in-app list). The accept-invitation page at `/invitations/:token/accept` renders each of the authorization outcomes per plan OP-6 with dignified messaging:

- Unauthenticated → redirected to login with the invitation URL preserved as return.
- Authenticated + valid + intended → confirmation → new Property Home.
- Authenticated + valid + wrong recipient → **403** outcome with clear, non-blaming copy.
- Not found → **404** outcome.
- Expired → distinct expired-invitation state (plan A-11 → HTTP 410 Gone).

## Relevant context and requirements

- **No in-app pending-invitations list.** The only entry point to acceptance is opening the shareable URL directly (plan OP-9 correction).
- **No signup, no account creation, no account switching offered.** If the authenticated identity does not match, present the 403 outcome and end the flow (plan OP-10).
- Copy must not imply that Donarium sent the URL (delivery is entirely external).
- Bilingual copy per EP-001.06.

## Constraints / established direction

- Return-URL preservation across login (some machinery in EP-001.01) applies to the invitation URL as well.
- Complies with plan hygiene **H-4** on any client-side error surfaces.

## Expected evidence
