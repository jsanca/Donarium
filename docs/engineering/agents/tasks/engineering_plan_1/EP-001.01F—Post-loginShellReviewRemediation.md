## Required remediation

### AAR-001 — Non-functional Sign out

The current Sign out control must not represent a successful logout while the
server session remains valid.

EP-001.01 prohibits backend changes and no logout endpoint currently exists.

Within that constraint:

- remove or disable the misleading Sign out capability;
- do not invent client-side session invalidation that cannot invalidate the
  httpOnly server session;
- do not introduce a backend logout endpoint in this task;
- preserve the authenticated shell otherwise.

If disabling rather than removing the control, the UI must not imply that logout
has occurred.

A real logout capability requires separately authorized backend work.

### AAR-002 — 401 from properties lookup

A 401 from `GET /api/properties` must not be interpreted as a legitimate
zero-property state.

Ensure authentication failure returns control to the authentication lifecycle so
the user is routed through the existing unauthenticated/login behavior.

Preserve the temporary 404 → zero-properties compatibility seam until EP-001.02,
as explicitly dispositioned by the review.

Do not reinterpret other HTTP failures as empty portfolio states.

### AAR-004 — ADR-003 contract accuracy

Reconcile ADR-003 with the actual accepted authentication surface after AAR-001
and AAR-002 remediation.

The ADR must describe the implementation truth and must not claim an available
`logout` capability unless one actually exists.

Do not redesign the routing decision.

### AAR-005 — Bilingual error/loading states

Replace the identified hardcoded-English shell/error/loading copy with the
existing i18n mechanism.

At minimum inspect and remediate the locations identified by the review:

- global error boundary;
- `RequireAuth` loading/error states;
- `RootRedirect` loading/error states;
- lazy-route `Suspense` fallback.

Prefer consuming existing translation keys where suitable rather than expanding
the i18n domain unnecessarily.

Do not take ownership of the graph reconciliation for EP-001.06.

### AAR-006 — Return-URL sanitizer duplication

Remove the divergent inline return-URL validation in `PublicOnly`.

Use the shared `sanitizeReturnUrl` behavior so security-sensitive return-URL
validation has one implementation.

Preserve existing successful return-URL behavior.
