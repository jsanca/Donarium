# EP-001.K01 — Knowledge Layout and Architecture Views Reconciliation

## Status

READY

## Classification

Derived execution work — Knowledge Reconciliation

## Assigned Role

knowledge-curator

## Origin

Derived from execution of EP-001 and accumulated repository knowledge drift.

The repository currently contains legacy and current documentation layouts,
including duplicated/competing agent locations and knowledge artifacts written
to legacy root locations.

This task also establishes current architectural views so a human can navigate
the implemented Donarium system without reverse-engineering the repository
from source on every inspection.

## Intent

Reconcile Donarium's current knowledge/documentation layout and produce
maintainable architectural views of the implementation as it exists now.

The result must:

1. remove obsolete/duplicate documentation layout ambiguity,
2. preserve knowledge and provenance while moving artifacts,
3. leave a single canonical engineering-agent hierarchy,
4. establish a clear canonical location for project knowledge,
5. document the current code structure through package-level structural
   diagrams,
6. provide a navigable module/package overview,
7. provide an ER diagram representing the actual current database schema.

This is knowledge reconciliation, not product implementation.

## Known Layout Tension

Current repository evidence includes both legacy and current structures such as:

    /knowledge/...
    /docs/knowledge/...

and competing agent/documentation locations including:

    /docs/agents/...
    /docs/engineering/agents/...

The canonical engineering-agent location is:

    /docs/engineering/agents/

Reconcile legacy agent material into that hierarchy and leave no competing
active agent root.

For knowledge artifacts, inspect the current documentation conventions,
README/OSK guidance, links, and artifact ownership and establish one canonical
knowledge hierarchy under `docs/`.

Do not delete knowledge merely because its current path is legacy.

## Scope A — Documentation Layout Reconciliation

Inspect at minimum:

- `/knowledge/`
- `/docs/knowledge/`
- `/docs/agents/`
- `/docs/engineering/agents/`
- `/docs/engineering/`
- documentation READMEs/indexes
- OSK/project documentation that declares paths
- references to these paths from source/documentation

Determine:

- which artifacts are canonical,
- which are legacy duplicates,
- which contain unique information,
- which references must be rewritten.

Reconcile them into the canonical layout.

### Required outcomes

- Exactly one active engineering-agent hierarchy:
  `docs/engineering/agents/`.
- No knowledge loss.
- Legacy material with unique content is moved/reconciled, not blindly deleted.
- Duplicate material is resolved deliberately.
- Internal Markdown links and relevant path references are updated.
- Existing engineering plan, reports, reviews, tasks and execution evidence
  remain reachable.
- Git history is not treated as a substitute for preserving currently relevant
  knowledge.

Record material reconciliation decisions.

## Scope B — Package Structural Diagrams

Create a structural diagram for each meaningful Donarium code package.

For Go packages, do NOT fabricate OO classes.

Represent as appropriate:

- structs,
- interfaces,
- important named/value types,
- composition,
- implementation/satisfaction relationships when useful,
- important dependencies between types,
- repository/service/runtime relationships,
- domain relationships.

Omit trivial implementation detail that makes a diagram unreadable.

At minimum cover the implemented server packages and meaningful client
architectural packages that currently participate in EP-001.

Prefer one diagram per package or cohesive package boundary rather than one
enormous diagram.

Each diagram must identify the source package it represents.

## Scope C — Navigable Module / Package Architecture View

Create a high-level architectural view showing the actual current module and
package structure of Donarium.

The view should make relationships such as these understandable where they
actually exist:

    client
    server
      domain packages
      application
      persistence/adapters
      HTTP/runtime
      platform
      identity
      properties

Do not impose this example if source differs; derive the view from the
repository.

The architecture view must allow a human reader to navigate from a package or
module toward its detailed structural diagram.

Use robust Markdown links as the canonical navigation mechanism.

Mermaid `click` navigation may additionally be used if supported by the chosen
renderer, but the documentation must remain navigable when Mermaid click
support is unavailable.

The goal is:

    Architecture overview
            ↓
       package/module
            ↓
    package structural view
            ↓
      relevant source

## Scope D — Database ER Diagram

Create an ER diagram representing the current database schema from migrations
and current persistence code.

Derive it from actual schema evidence, not from desired future product design.

Include at minimum currently implemented entities and relations such as,
where present:

- installations/bootstrap-related persistence,
- users,
- credentials,
- organizations,
- memberships,
- platform grants,
- properties,
- property stakeholders,

plus any other current tables discovered during inspection.

Represent:

- primary keys,
- material foreign keys,
- cardinality,
- important relationship tables,
- discriminated Party persistence where relevant.

Where database constraints cannot be represented cleanly in Mermaid ER syntax,
add concise notes next to the diagram rather than distorting the model.

Do not include future Invitation, Payment, Lease, Unit, or other tables unless
they actually exist in the current schema.

## Artifact Organization

Create a coherent architecture documentation hierarchy under the reconciled
canonical `docs/knowledge/` area.

A reasonable shape is:

    docs/knowledge/
    ├── README.md
    ├── architecture/
    │   ├── README.md
    │   ├── modules-and-packages.md
    │   ├── database-er.md
    │   └── packages/
    │       ├── <package>.md
    │       └── ...
    ├── decisions/
    │   ├── ADR-001-...
    │   └── ...
    └── ...

This shape is a guideline, not authority.

Inspect existing repository conventions and use the smallest coherent
hierarchy that satisfies navigation and reconciliation.

Avoid gratuitous directory depth.

## Diagram Requirements

Prefer Mermaid embedded in Markdown so diagrams remain versioned, diffable and
editable with the repository.

Diagrams must describe current implementation.

Every architectural diagram must state:

- what source/evidence it represents,
- its scope,
- any meaningful omissions.

Do not turn diagrams into speculative architecture.

## Reconciliation Requirements

While moving artifacts:

- preserve ADR numbering and identity,
- preserve engineering-plan identity,
- preserve report/review/task provenance,
- update relative links,
- detect stale references to legacy paths,
- avoid duplicate canonical copies,
- distinguish historical evidence from current canonical knowledge.

If two artifacts conflict semantically, do not silently choose one.

Classify the conflict and either:

- reconcile it when knowledge-curator authority is sufficient, or
- record/escalate it when Product Architect or another Role owns the semantic
  decision.

## Verification

Verify at minimum:

- repository search finds no active references to obsolete agent paths except
  deliberate historical references,
- canonical documentation links resolve,
- ADR cross-links resolve,
- engineering plan/task/report/review references remain valid,
- architecture index links reach package diagrams,
- package diagrams correspond to actual packages/types,
- ER diagram corresponds to current migrations,
- no application/source behavior was modified.

Where practical, use repository tooling to check Markdown/internal links.

## Deliverables

Produce:

1. Reconciled documentation/knowledge directory layout.
2. One canonical `docs/engineering/agents/` hierarchy.
3. Canonical knowledge hierarchy under `docs/`.
4. Updated references affected by moves.
5. Architecture/module/package overview.
6. Structural diagrams for meaningful packages.
7. Current database ER diagram.
8. Architecture/knowledge index enabling human navigation.
9. Durable reconciliation report describing:
   - what moved,
   - what merged,
   - what was removed as duplicate,
   - what remained historical,
   - links updated,
   - conflicts discovered,
   - unresolved/escalated items.
10. Update `docs/engineering/ENGINEERING_LOG.md` as appropriate.

## Constraints

Do not:

- change application behavior,
- refactor production code,
- change database migrations,
- invent future domain entities,
- rewrite accepted ADR decisions merely to make diagrams prettier,
- duplicate artifacts simply to support multiple layouts,
- create a large taxonomy when a shallow index is sufficient.

Filesystem organization exists primarily to improve human scanning.
Precise semantics remain in the artifacts and their links.

## Stop Condition

STOP after:

1. repository knowledge/layout has been reconciled,
2. architecture/package diagrams have been created,
3. database ER has been created,
4. navigation/indexes and affected links have been verified,
5. reconciliation evidence/report has been produced,
6. Engineering Log has been updated as appropriate.

Report any semantic conflict requiring another Role rather than resolving it
outside knowledge-curator authority.
